# 方案：内存到线提醒

> 状态：待开发。对应 `docs/FEATURE_CANDIDATES.md` 候选 4。
> 基于 `main` 分支 0.2.0 的代码写成，行号可能随后续提交变化，以函数名和组件名为准。

## 1. 要解决的问题

内存监控每 2 秒采样一次，超过警戒线时只做一件事：把主窗口侧栏和两个悬浮窗里的内存数字变红。打游戏时这几处都不在视线里，等发现时往往已经卡了。

本方案让它在到线时**走现成的提醒出口**：响铃 + 任务栏闪烁 + 右下角弹窗，和开服提醒、金价提醒一样。

先说清楚这里的「内存」是什么：`memory.rs` 采的是**整台电脑的物理内存占用率**（`sysinfo` 的已用 ÷ 总量），不是游戏进程自己的占用。本方案不改变这个口径。

## 2. 触发规则

核心是不能吵。内存在警戒线附近上下抖是常态，每次过线都响，用户一晚上就会把它关掉。规则照金价提醒（`meso_alert.rs`）的思路：只在「跨过去」的那一下响，退回去够远才重新上膛。

| 规则 | 建议值 | 说明 |
| --- | --- | --- |
| 持续才算 | 连续 30 秒都在线上（15 次采样） | 中间有一次掉到线下就重新计数。挡住开程序、切场景时的瞬时尖峰 |
| 响一次后上膛条件 | 占用回落到「警戒线 − 5 个百分点」以下 | 例如线是 85%，要回到 80% 以下才允许下一次。挡住在线上下来回抖 |
| 最短间隔 | 两次提醒至少隔 10 分钟 | 兜底。即使规则上已经重新上膛也不连响 |
| 只在游戏开着时响 | 是 | 见第 7 节拍板点 1 |

三个数值是我给的起点，没有实测依据，开发时写成常量并加注释，上线后按群里反馈调。

**状态变化时怎么处理**

- **改了警戒线**：清掉「已经响过」的状态和持续计数，按新线重新判断。和金价提醒改阈值的处理一致。
- **开关从关到开**：同样重新判断。如果当时已经在线上，持续 30 秒后响一次（用户刚打开就该知道现在是超的）。
- **程序重启**：状态只存在内存里，不落库。重启后如果仍在线上会再响一次，可接受。
- **一直在线上**（比如 8GB 的机器开着游戏常年 90%）：整个运行期间只响一次，之后不再上膛。这种情况下用户该做的是调高警戒线，提醒文案里不用专门说。

## 3. 交互与界面

### 3.1 开关的位置

「设置 → 悬浮窗与内存」里现有的「物理内存警戒阈值」卡片，滑块下方加一行开关：**到线时提醒**。

卡片说明那句话相应改掉。现在是：

> 内存占用到这个比例时，主窗口侧栏与悬浮窗里的内存显示会变红，提醒你进商城刷新内存。

改成一句能同时覆盖两种状态的，例如：

> 内存占用到这个比例时显示变红；打开下面的开关，还会响铃并弹窗提醒。

总览页「提醒」小卡片里现在有「开服提醒」「黑名单命中」两个开关，加第三个「内存到线」，写的是同一个设置。

### 3.2 弹窗内容

沿用 `AlertToastView`，不改布局。

- 标题：`⚠️ 内存占用到线了`
- 来源行：`内存到线提醒 · 时间`
- 正文：`内存占用 87%（已用 13.9 GB / 共 16 GB），到了你设的 85% 警戒线。建议进商城刷新。`
- 图标：`Cpu`（和设置卡片上用的是同一个）
- 边框配色用默认的琥珀色，不用黑名单那种红色（红色留给「可能被骗」）。

「建议进商城刷新」是界面上现有的说法（`MainView.tsx` 侧栏），这里原样沿用。它背后的游戏机制我没有依据核实，所以不扩写、不解释原理。

### 3.3 不新增测试按钮

「提醒」页现有的「测试开服提醒」验证的就是同一条出口（响铃、闪任务栏、弹窗）。那个能响，内存提醒就能响，不需要再加一个。

「提醒」页底部现有的一句说明写的是「两种提醒走同一个出口」，数量已经对不上（实际还有黑名单命中），顺手改成不带数量的说法。

## 4. 涉及的文件与改动点

### Rust 侧

| 文件 | 改动 |
| --- | --- |
| `src-tauri/src/memory.rs` | ① `MemoryMonitor` 加一个提醒开关（`AtomicBool`，写法照现有的 `threshold`）和对应的 `set_alert_enabled`；② 新增**纯函数**判定，输入是「当前占用、警戒线、开关、游戏是否在跑、上一次状态、现在时刻」，输出是「这次响不响 + 新状态」，照 `meso_alert::decide` 的形态写，不碰 `AppHandle`；③ 采样循环里每轮调一次判定，该响时调 `alert::fire_memory_alert`；④ `set_threshold` 和开关变化时把判定状态清零 |
| `src-tauri/src/alert.rs` | ① `AlertSource` 加 `Memory`，补上 `code()`（`"memory"`）、`label()`（`内存到线提醒`）、`title()` 三处；② 新增 `fire_memory_alert(app, body)`，照 `fire_meso_alert` 写：记一条提醒历史（`kind` 用 `memory_high`）再 `dispatch`，**不走**开服提醒那个 10 分钟冷却（节流由 `memory.rs` 的判定负责，两件事共用一个冷却会互相吃掉）；③ 模块文档开头那段「三类内容共用……关注物品跌破价格阈值」已经过时（关注清单在 0.1.4 删了），顺手改成现状 |
| `src-tauri/src/db.rs` | ① `AppSettings` 加 `memory_alert_enabled: bool`；② `get_all_settings` 里读设置键 `memory_alert_enabled`；③ 默认值见第 7 节拍板点 2 |
| `src-tauri/src/commands.rs` | 新增命令 `set_memory_alert(enabled: bool)`：写设置表 + 更新 `MemoryMonitor` 的开关。照 `set_memory_threshold` 和 `set_blacklist_watch` 的写法做成独立命令，不塞进 `patch_settings` |
| `src-tauri/src/lib.rs` | ① 启动时把库里的开关值传给 `MemoryMonitor`；② `generate_handler!` 里注册 `set_memory_alert` |

**「游戏是否在跑」怎么判断**：复用 `exp::capture::find_game_window()`（经验统计和校准都在用它），找得到窗口就算在跑。不要为此新写一套进程检测。它每 2 秒被多调一次的开销需要开发时看一眼；如果嫌重，可以只在占用已经过线时才去查。

**线程约定**：`fire_memory_alert` 是从 `memory.rs` 的异步采样循环里调的，和 `meso_alert` 的调用位置同类，不在 UI 线程回调里，符合项目「回调里只投递不操作」的约定。`cargo test ui_thread_callbacks` 会自动检查。

## 5. 数据与边界情况

| 情况 | 处理 |
| --- | --- |
| 警戒线附近来回抖 | 由「持续 30 秒」和「回落 5 个百分点才上膛」两条挡住 |
| 滑块拖动过程中 | 现有逻辑是松手才提交，拖动中途的值不会进到后端，不会误触发 |
| 采样拿不到数据（总量为 0） | 现有代码此时占用率算作 0，不会触发。保持 |
| 电脑睡眠后唤醒 | 最短间隔用单调时钟计，睡眠期间的时间算不算进去取决于系统，最坏情况是唤醒后多等一会儿才能响，不会误响 |
| 提醒窗正开着时又来一次别的提醒 | 现有逻辑是新内容顶掉旧内容，`alert_generation` 保证旧的计时器不会关掉新窗。不用改 |
| 和开服提醒同时发生 | 两者冷却独立，都会响。后到的顶掉先到的弹窗，两条都会记进提醒历史 |
| 游戏没开时内存超线 | 默认不响（见拍板点 1）。界面上照常变红 |
| 开关关着 | 判定函数直接返回不响，并且不累计持续时间。界面变红的行为不受影响 |
| 老用户升级 | 设置表里没有这个键，取默认值（见拍板点 2） |
| 提醒历史 | 每次提醒会往 `alert_history` 表写一条。这张表目前没有界面入口也没有条数上限（见 `docs/FEATURE_CANDIDATES.md` 第四部分），内存提醒在规则约束下一天最多几条，不会明显加剧 |

## 6. 验收要点

**自动化（必须有）**

判定是纯函数，全部用单测钉住，不依赖真机内存：

1. 占用一直在线下 → 不响。
2. 过线但不满 30 秒就回落 → 不响，计数清零。
3. 连续 30 秒在线上 → 响一次。
4. 响过之后继续在线上 → 不再响。
5. 响过之后回落到线下 3 个百分点再回升 → 不响（没退够）。
6. 响过之后回落到线下 5 个百分点以上再回升并持续 30 秒 → 距上次不满 10 分钟不响，满了才响。
7. 开关关着 → 任何情况都不响。
8. 游戏没在跑 → 不响（按拍板点 1 的结论）。
9. 改警戒线后状态清零：原来在「已响过」，改完如果仍在新线上，持续 30 秒后会再响一次。

`cd src-tauri && cargo test` 全过，包括 `ui_thread_callbacks` 约定检查。

**手动**

1. 游戏开着，把警戒线拖到比当前占用低几个点，打开开关：约 30 秒后响铃、任务栏闪、右下角弹窗，标题和正文里的数字与侧栏显示一致。
2. 弹窗不抢游戏焦点；20 秒后自动关；点「知道了」立刻关。
3. 保持在线上再等几分钟：不再响。
4. 把警戒线拖回高位再拖低：重新判断，约 30 秒后再响一次。
5. 关掉开关重复第 1 步：只变红，不响。
6. 关掉游戏重复第 1 步：只变红，不响。
7. 「设置」和「总览」两处的开关是同一个值：改一处，切到另一页看到的是改后的状态。
8. 重启程序后开关状态还在。
9. 日间、夜间主题下开关和弹窗都看得清。
10. 浏览器里 `?window=main&mock` 和 `?window=alert&mock` 不报错。

## 7. 需要你拍板的点

| # | 问题 | 我的建议 | 理由 |
| --- | --- | --- | --- |
| 1 | 只在游戏开着时提醒，还是任何时候都提醒？ | 只在游戏开着时 | 这个工具默认关窗收进托盘常驻。不限制的话，用户没在玩游戏、开着别的大程序时也会被响铃，而那时「进商城刷新」这条建议根本用不上 |
| 2 | 默认开还是默认关？（上一轮的问题 6，还没答复） | 默认开 | 这个功能的价值就在「不用自己想起来看」，默认关的话大多数人不会知道有它。老用户升级后会多一种响铃，但有上面的规则约束不会频繁，更新说明里写明并说清在哪关 |
| 3 | 持续 30 秒 / 回落 5 个百分点 / 最短 10 分钟，这三个数接受吗？ | 先按这个发 | 没有实测依据，是参照金价提醒定的起点，发出去后按群里反馈调 |
| 4 | 总览页「提醒」卡片要不要加第三个开关？ | 加 | 另外两种提醒的开关都在那里，只缺这一个反而奇怪。嫌挤可以不加，只留设置页那一处 |
